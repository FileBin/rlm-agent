# Заметка агента — шаблон

> Рабочий скретчпад. Описывает **текущее состояние**, а не историю работы.
> Перезаписывай целиком при каждом обновлении. Лимит — 30 строк.
> Не отчёт и не доказательство: истина — артефакты на диске и вывод проверок.

---

## Заголовок

- **Задача:** `<краткое имя задачи, как в plan/todo.md>`
- **Роль:** `planner | developer | tester`
- **Веха:** `<M1 — название>`
- **Шаг:** `<M1.2 — ID и формулировка из todo.md>`
- **Обновлено:** `<итерация N>`

## Статус

`in_progress | done | blocked | failed`

<одно предложение: что происходит сейчас>

## Прогресс

- [x] <что реально сделано, с указанием файла/команды>
- [x] <...>
- [ ] <что начато, но не закончено>

## Блокеры

- <блокер> → <кто/что нужно, чтобы снять> · ожидает с итерации `<N>`
- <нет блокеров — так и напиши: `нет`>

## Следующий шаг

1. <конкретное действие, с которого продолжишь — не «продолжить работу»>
2. <...>

## Заметки

<до 3 строк: решение, которое неочевидно; текст ошибки — максимум 3 строки; ссылка на knowledge_base, если опирался>

---

## Правила заполнения

1. **Перезапись, не дописывание.** Файл — снимок состояния. История живёт в git оркестратора и в отчётах QA.
2. **Лимит 30 строк.** Не влезает — ты записываешь лог. Оставь только то, без чего следующий вызов начнётся с нуля.
3. **Прогресс — только подтверждённое.** `[x]` ставится, если файл записан или команда выполнена. «Скорее всего работает» — это `[ ]` и блокер.
4. **Блокер — с адресатом.** «Нет сети для fetchurl → нужен pre-fetch в store (Планировщик)» полезен; «не получается» — нет.
5. **Один следующий шаг.** Список из десяти «надо бы» — признак, что шаг из плана слишком крупный.
6. **Без дампов.** Никаких полных выводов сборки, кусков кода, рассуждений. Текст ошибки — максимум 3 строки, остальное в лог/отчёт.
7. **Пустые разделы не оставляй** — пиши `нет`.

## Пример (заполненный, для developer)

```markdown
## Заголовок

- [ ] checks для AC1

## Блокеры

Опора: knowledge_base/patterns/003-wine-wrapper.md

```
